# First-principles review, 2026-11-01

Every basic decision in the app, argued against from the user's real job:
running several projects at once, each with a main Claude session that
dispatches work into worker panes, plus their boards, notes and docs. The
recorded decisions and rules are what is under review here, not the
authority. Speed and memory are the profiling card's (dca04e6f) and are left
out.

Sources: the feature docs, the code where a decision is enforced (cited as
`file:line`), the git history of this repository, and a demo instance of the
installed 2.41.1 build run with its own `HOME` and `--user-data-dir`. Anything
marked **opinion** is a judgement the evidence does not settle.

## Top five changes

1. **Stop merging `board.json` through every pull request** (W1). It is in 82
   of the 115 conflicted merges. Every card branch edits the same file, so
   every parallel pair conflicts on it.
2. **Let the shells outlive the app** (R1). Today a restart, a rebuild or a
   crash kills every pane. workflow-rule-1, the resume machinery and half of
   errors-decision-3 exist only to work around that.
3. **Bind the remote host to localhost or put TLS on it** (S1). Turned on, it
   listens on every interface in plain `ws://`, and a connected screen can
   type into any shell.
4. **Write the board as operations against a fresh read** (R2). The app saves
   its whole in-memory board, so it can erase a move an agent just made.
5. **Tell main when a worker is done** (W4). The app knows (the Stop hook
   tells it) but only marks the pane. Main does not hear about it unless the
   worker's own SendMessage arrives.

## Top five that held up

1. **A worktree per card** (W6). Parallel agents need separate checkouts, and
   git worktrees are the cheapest way to get them.
2. **The process split, enforced by lint** (A1). It catches a `node:fs`
   import in a view before the build does, at no cost to any change.
3. **A failure nobody caught keeps the app running** (R6). Every pane's work
   lives inside the process, so ending it is the worst possible answer.
4. **Keyboard first, mode keys pass through** (U1). It is the reason the app
   is faster than a mouse dashboard, and the pass-through keeps nvim and the
   shell whole.
5. **A decision gets its own module and a test** (P2). Tests are 22% of the
   changed lines, and they are where regressions get caught in a codebase with
   no DOM test environment.

## Findings, ranked by impact

Each entry: what the decision is, the case against it, the best alternative,
the cost of switching, and the verdict.

### W1. The board is a tracked file that every card branch edits — change

**What.** `.dashboard/board.json` is in git. A card's agent moves its card on
the branch (`board: start`, then `is ready`). The ship commits the Ship move on
the worktree's board (`src/main/ship/ship-flow.ts:35-48`). board-rule-2 makes
the move into Done happen on the branch before the merge.

**Against.** Two cards running in parallel both rewrite the one file, so the
second one to merge always conflicts on it. 82 of the 115 conflicted merges
list `board.json`. The user's instructions have grown a workaround: follow-up
cards go through `/create-task` straight to main, "so the two parallel PRs do
not fight over .dashboard/board.json". board-rule-2 is a second workaround:
the board on `main` drifted from the screen because a move made after the
merge never reached `main`.

**Example.** Today: cards A and B start from the same `main`. A merges. B's
pull request now conflicts on `board.json`, the agent merges `origin/main` and
resolves the JSON by hand, and a resolution that keeps the wrong side moves a
card back a column. With the alternative, A and B touch different files and B
merges clean.

**Alternative.** One file per card, `.dashboard/cards/<id>.json`. Columns and
order go in a small `board.json` that only the app writes on `main`. Two cards
then conflict only when both edit the same card. A further step would take the
board out of git and keep it in user data, but then the board is no longer
shared with the repository, which was the point of tracking it.

**Cost.** Large. `board-store.ts`, the CLI, the watcher (folder already, so
that part holds) and a one-time migration.

### R1. Shells die with the app — change

**What.** Every pane is a `pty.spawn` child of Electron main
(`src/main/main.ts:408-414`), with no detach. On quit every shell is killed
(`main.ts:960-961`). `session.ts:7-8` says it: "every pane comes back empty".

**Against.** The user's job is long-running agents. A restart costs every
running task, and the app answers with a set of compensations rather than a
fix: workflow-rule-1 (never restart), errors-decision-3 (never exit), Claude
resume after restart (`claude-resume.ts`, `resume-ledger.ts`, `dispatched`
panes in `session.json`), and a quit dialog. Each new version of the app needs
a restart to install, so every update costs the work in flight.

**Example.** Today: a rebuild lands while three workers are mid-card. The
restart kills them. Their conversations resume, but any `npm test` or dev
server they were running is gone, and a worker resumed mid-turn starts its
turn over. With a pane server, the app restarts, reattaches and the three
shells are still on the same line.

**Alternative.** Host the ptys in a process that outlives the window: tmux in
control mode (`tmux -C`), or a small pty daemon over the session socket that
the app reconnects to. xterm.js stays the front end.

**Cost.** Large. It touches the pane lifecycle and the busy check
(`process-tree.ts`), and it makes the resume code largely unnecessary.

### S1. The remote host listens on every interface in plain ws — change

**What.** `new WebSocketServer({ port, maxPayload })` with no `host`
(`src/main/remote-host/remote-host.ts:30`) binds 0.0.0.0. The client dials
`ws://` (`remote-client.ts:80`). The token is compared with `!==`
(`remote-protocol.ts:80-81`) with no lockout. A joined screen reaches every
channel except a short denylist (`remote-protocol.ts:32-35`), including
`pty:input` (`pane-channels.ts:37-39`) and `task:run`. It is off unless
`host.port` is set (`settings.ts:64`).

**Against.** Anyone on the same network who sees one connection's hello has
the token in clear text, and with it a shell on the host as the user. A café or
office Wi-Fi is enough. The design spec meant a second screen on the user's own
machines, which does not need the open port.

**Alternative.** Bind `127.0.0.1` by default and reach it over an SSH tunnel
or Tailscale. Opening to the network becomes a setting, and when it is on the
host serves `wss://`. Also compare tokens with `timingSafeEqual`.

**Cost.** Small for the bind and the compare, medium for TLS.

### R2. The app saves its whole in-memory board — change

**What.** `save()` sends `state.board` whole (`src/renderer/board/board-view.ts:268`),
and `board:write` writes it as given (`project-files-ipc.ts:38-41`). The
renderer picks up outside writes only when the watcher's `board:change`
arrives, and only on the board view (`renderer.ts:741-745`,
`board-view.ts:223-226`). The CLI re-reads and re-runs its command just before
writing, and calls a lock "the next rung" (`board-cli.ts:247-263`).

**Against.** board-rule-1 exists so two writers do not disagree, but the two
writers still overwrite each other. The CLI's side is already narrow; the
app's is as wide as the gap between an agent's write and the watcher event
reaching the board view.

**Example.** An agent runs `board move <id> Review` while you are renaming a
card on the same board. If your save lands before the watcher's reload, the
file holds your board from a moment ago, and the agent's move is gone with no
message.

**Alternative.** Send operations (`move`, `set`, `comment`) to main. Main
applies each to a fresh read and writes it, the way `runBoardCommandOnLatest`
already does for the CLI. Both writers then share one path in main.

**Cost.** Medium. `board-view.ts` and `board-writes.ts` change their calls,
and the operations already exist in `board.ts`.

### W4. Main is not told when a worker finishes — change

**What.** A worker's prompt ends with "SendMessage to main-<slug> when done"
(`src/main/workers/dispatch.ts:95`). The app delivers nothing itself. The
Stop hook runs `session notify <id> done`, which marks the pane green
(`session-requests.ts:190-197`). workers-decision-1 records why the hook does
not message main: no command sends to a named session.

**Against.** That reason holds for a terminal main. Main is now the app's own
SDK session (workers-decision-1, `chat-sessions.ts`), and the app can push a
prompt into it, the same way the screen sends one. Whether SendMessage reaches
an SDK session is not decided in this repository, so today the one report main
can count on is the one it has to ask `pane list` for.

**Example.** Today: you dispatch three tasks and go to another project. Two
workers finish, and one of them forgot its SendMessage. Main sits idle until
you come back and ask it. With the alternative, the hook's `done` puts
"terminal-3 is done: <its last message>" in main's queue and main carries on.

**Alternative.** On `notify done` for a pane that main dispatched, queue a
short user message into main's session through the existing queue
(chat-decision-7).

**Cost.** Small to medium.

### W2. Every card bumps `package.json` — change

**What.** workflow-rule-3: every merged card bumps `version`, last, after
merging `origin/main`. The work-card skill spends three paragraphs on how.

**Against.** The goal is to tell an installed build from `main`. The bump
does that poorly: two cards that both started on 2.41.0 both say 2.41.1 when
one merges after the other opened its pull request, and the skill says so
("This narrows the window but does not close it"). It also costs 13
`package.json` and 12 lockfile conflicts, plus the ritual on every card.

**Example.** Today the foot of the manager page says `v2.41.1`, and two
builds can say that with different code. With the alternative it says
`v2.41.1+270c22f`, and `git log 270c22f..main` lists what the installed build
is missing.

**Alternative.** Stamp the commit at build time (`version.ts` already reads
the version at build) and bump the semver only when releasing.

**Cost.** Small.

### U2. The help dialog has become the manual — change

**What.** keys-rule-2 makes every change update `src/renderer/keys/help.ts`,
and each screen opens with a blurb.

**Against.** The rule works: Ctrl+H is up to date. But nothing caps the
blurb, so each change appends a sentence to it. On the terminals view the
dialog is 4,563 words, and the first key comes after a 1,129-word paragraph
that covers `projects.yaml`, `pane claim --project` and the manager's
terminals (measured in the demo). `help.ts` conflicted 18 times.

**Example.** Today you press Ctrl+H to find the fold key and scroll past four
screens of prose. With a cap, the blurb is two sentences and the keys start
on the first screen.

**Alternative.** Cap each blurb (about 60 words) with a test in
`help.test.ts`. Detail moves to `docs/<feature>/README.md`, which the drawer
already shows rendered.

**Cost.** Small.

### U3. A project can only be opened through the OS folder dialog — change

**What.** The picker lists recent projects. "Open a new project…" calls
`dialog.showOpenDialog` (`main.ts:521-529`). A path typed into the search box
only filters the recents (`picker.ts:55-58`). A remote screen is refused the
dialog with "Type the folder's path on the host" (`screens.ts:11`).

**Against.** conventions-rule-1 says every action is reachable from the
keyboard. On a first launch, the only way in is a GTK or macOS folder dialog.
A remote screen cannot open a new folder at all except through
`dashboard project open` from a pane, which needs `projects.yaml`.

**Example.** In the demo: Ctrl+S, type the project's full path, and the list
offers only "Open a new project…" and "Connect to a host…". With the
alternative, a typed path that is an existing folder becomes the first row,
and Enter opens it, on a remote screen too.

**Alternative.** That row. `projects:open` already takes a path.

**Cost.** Small.

### R3. No single-instance lock, and `session.json` is not written atomically — change

**What.** `requestSingleInstanceLock` appears nowhere in `src/`. Two copies
share `settings.json`, `session.json`, `recents.json`, `worktrees.json` and
`session-index.json`, and the last writer wins. `session.json` and recents are
plain `writeFileSync` (`session.ts:81`, `projects.ts:53`). A damaged
`session.json` reads as empty (`session.ts:71-77`). Notes are debounced
400 ms; the quit dialog asks before the window goes, which is far longer than
that (`notes-view.ts:41-47`), so only a crash within 400 ms of typing loses
anything, and that is not worth a change.

**Against.** A second launch from a launcher or a stray `Dashboard` command
opens a second app on the same files. A kill during a `session.json` write
leaves a truncated file, and the next launch opens no projects.

**Example.** Today: the machine loses power while a sweep writes
`session.json`. On the next launch, all eight projects are gone from the tabs
and have to be found again. With the alternative, the file is the old one or
the new one, never half.

**Alternative.** Take the lock and focus the running window, but let a
`--user-data-dir` copy through so demo instances still work. Write
`session.json` and recents with the `replaceFile` that the board and chat
sessions already use (`board-store.ts:371-385`).

**Cost.** Small.

### W3. The review agent merges with no person in the loop — change (opinion)

**What.** When a card's pull request appears, the review sweep moves the card
to Review, takes the worktree and starts an agent told to run `/pr-loop`. If
the loop converges, the agent runs `gh pr merge N --merge` itself
(`src/main/ship/review.ts:117-131`). The prompt says not to approve.

**Against.** board-rule-2 calls Review "a pull request open and nothing has
checked it", for the person whose job it is to look. In practice Review is a
stop the card passes through on the way to an automatic merge. The only gate is
one model reading another model's review loop. Untagged human threads do block
it, but only if a human wrote one in time.

**For it.** Throughput is the reason the app exists, and a merge that waits
for the user is a queue that grows while they sleep. That is why this is an
opinion.

**Example.** Today: a card that changes how the board writes its file
converges in `/pr-loop` overnight and merges. In the morning `main` has a
change you never read. With the alternative, it waits on the manager's queue
at "ready to merge", and one key merges it.

**Alternative.** Stop at "converged", put the card on the needs-you queue
(`needs-you.ts` already lists Review cards nothing is reviewing), and make
merge one key there. A per-project setting could keep auto-merge for projects
where that is wanted.

**Cost.** Small.

### W5. The instructions for where a finished card goes disagree — change

**What.** The global instructions say to move a card to Done when its pull
request is ready. The work-card skill says Done
(`~/.claude/commands/work-card.md:39-51`). This repository's CLAUDE.md says
Review, and says it "beats" the global rule (board-rule-2). The review prompt
then moves it to Done again, on the branch and on the app's board.

**Against.** Every agent reads three instructions and has to pick a winner.
This card's own dispatch had to say "move the card to Review" to override the
skill it was run with.

**Example.** An agent that follows the skill moves its card to Done while the
pull request is open, and the board says shipped about unreviewed work. With
the alternative, there is one rule in one place.

**Alternative.** The skill reads the target column from the project (Review
when the board has one), and the global line goes.

**Cost.** Small, but outside this repository (dotfiles).

### P1. A history file per feature, appended by every pull request — change

**What.** Each feature keeps `history.md`, one line per merged change.

**Against.** It repeats the pull request titles that `git log --merges`
already holds, and because every pull request appends to the end of the same
file, it conflicted in 72 of the 115 conflicted merges (66 in
`docs/chat/history.md` alone), nearly as often as `board.json` (82).

**Alternative.** Mark the history files `merge=union` in `.gitattributes`, so
two appended lines both survive with no conflict. Dropping the files is the
other choice, but they are the one place that ties a pull request to a
decision id, which `git log` does not.

**Cost.** Small: one line in `.gitattributes`. For that cost it is the
cheapest fix for the second-largest source of conflicts, so it belongs beside
W1 in the top changes, not at its rank in this list.

### S2. No Content-Security-Policy on the window — change

**What.** `index.html` has no CSP and nothing sets one. Model output is
rendered as `innerHTML` (`chat-entries.ts:86`, `doc-viewer.ts:16`). `marked`
escapes raw HTML and `safeLink` filters links (`chat-markdown.ts:46, 51-56`).
`contextIsolation` and `sandbox` are Electron 45's defaults (on).

**Against.** The escaping is the only line of defence against a prompt-
injected reply or a doc in a cloned repo that carries markup. One renderer
bug, such as a highlight.js language that emits raw HTML, and a script runs
with the preload bridge in reach, which can write to any pty.

**Alternative.** A meta CSP: `default-src 'self'; script-src 'self';
img-src 'self' data: blob:; style-src 'self' 'unsafe-inline';
connect-src 'self' data:; frame-src blob:`. The last two are needed because a
PDF in the Claude screen is fetched from a `data:` URL
(`chat-view.ts:486`) and shown in an iframe on a `blob:` URL
(`overlay.ts:86-87`).

**Cost.** Small. Check by hand: open a PDF tile and a doc with an image in
the drawer.

### C1. Two ways to run Claude, and the Claude screen chases the CLI — change (opinion)

**What.** Main is an Agent SDK `query()` drawn as HTML (chat-decision-1,
workers-decision-1). Workers, card agents and the reviewer are the CLI in
panes. The screen re-implements what the TUI draws: `/resume`, `/rewind`,
`/model`, `/effort`, `/diff`, `/mcp`, `/btw`, `/export`, `/copy`, the stash,
the readline keys, and the queue. That is 37 pull requests in four days and
4,791 lines, and two of the calls it relies on are missing from the SDK's
types (`cancelAsyncMessage`, `askSideQuestion`; app/README dependency holds).

**Against.** Every Claude Code release adds TUI features the screen does not
have, so parity is a treadmill. And each undeclared call can break on an SDK
bump with the tests still green. Two ways to run Claude also means two status
paths (hooks for panes, the SDK stream for main), two resume paths and two
token stories (per-pane figures exist only for panes,
`pane-sessions.ts:1-7`).

**For it.** The screen does things a pane cannot: permission asks in the
app's own box, images and PDFs inline, and a session the app can push into
(which W4 needs). Main's job is talking to the user, not running tools, and
rich rendering serves that.

**Alternative.** Keep the screen, and stop chasing parity. Each new command
has to name what the user does with it that a worker pane, which is the CLI
itself, cannot do. Going back to main as a CLI pane would delete 4,791 lines,
but it would also lose W4's push and the permission box.

**Cost.** Small for the freeze. Large for going back, which is not
recommended.

### U4. Market cards lead the manager page — change (opinion)

**What.** The top of the manager page, about 190 px across the full width, is
four cards: the date and weather, Bitcoin, Tether in toman, and gold (seen in
the demo).

**Against.** The manager page's job is "what wants you". The first thing on
it is prices that change nothing the user does there, and the needs-you list
starts below them.

**Alternative.** One line along the foot beside the version, or its own
section on the strip.

**Cost.** Small.

### Decisions that survive

One line each on why the case against failed.

**Product and platform**

- **A dashboard of terminals, a main plus workers (product shape).** The
  alternative, fewer and better-supervised agents, is what main already is: a
  supervisor the user talks to while the workers do the work. The panes are
  where the user watches them, and the needs-you queue is what makes many of
  them bearable.
- **Electron + xterm.js + node-pty.** A native app or a TUI would lose the
  HTML board, chat and viewer, and xterm.js is the terminal VS Code ships. R1
  changes where the ptys live, not this choice.
- **One window, a page per project.** The second-screen case is covered by
  the remote host, and a second window would bring R3's shared files with it.

**Architecture**

- **main/renderer/preload/shared, enforced by eslint (A1).** It caught 58
  cross-process imports when `src/` split (app-rule-2), and it costs a change
  nothing.
- **IPC `<noun>:<verb>`.** Free to follow, and it keeps the channels sorted
  together by noun.
- **A refusal is answered as a value (errors-rule-2).** It is the difference
  between a sentence and Electron's "Error invoking remote method" on screen.
- **Main owns the open projects (remote-host-decision-1).** With two screens
  there has to be one owner, and the host is the only one both can reach.
- **Watching the `.dashboard` folder, not the file.** A rename over the file
  breaks a file watch, as board-rule-1 says.
- **Polling worktrees every 5 s and `~/.claude` every 30 s.** Incremental by
  size (`usage-store.ts:68-92`), with no watch on a tree of thousands of files.
- **State split: tracked board and notes in `.dashboard/`, personal state in
  user data.** Conversations and the session index are one person's, and the
  board is the project's. W1 changes the board's shape, not where it lives.
- **The session socket trusts any caller as the same user.** The folder is
  mode 0700 (`session-socket.test.ts:24`), and any process running as the
  same user can already type into the same shells.

**Work model**

- **A worktree per card (W6).** Parallel agents need separate checkouts, and
  a worktree shares the object store.
- **Ship is a column, not a key.** Moving a card right is the gesture the
  board already has, and conventions-rule-1's active-board rule closes the
  wrong-board case it opened.
- **Doing and Backlog as plain labels.** They cost nothing, and agents and
  people both read them.
- **Workers in `--permission-mode auto`.** A worker that stops at every
  prompt blocks the queue. Auto mode keeps the classifier, and a blocked
  worker raises a yellow edge and a notification.
- **An exact name for `pane claim --project` (workers-decision-2).** A fuzzy
  match that guesses wrong starts a worker in the wrong checkout.
- **The app's own session index (drawer-decision-1).** `~/.claude/projects/`
  splits a project's worktrees across slug folders.

**UX**

- **Keyboard first, mode keys pass through (U1).** Taking Ctrl+N mid-word in
  nvim is what the rule prevents, and the which-key strip makes the keys
  findable.
- **The manager tab.** It is the only place where "which of my eight projects
  wants me" has one answer.
- **The drawer as a viewer, not a pane (drawer-decision-2).** A doc you read
  once should not take a pane slot.
- **The settings file keeps only what you changed (errors-decision-1).** A
  shipped default can then move.

**Process**

- **Docs per feature with rules and decisions.** They are 10% of the changed
  lines, and this review could only argue with decisions because their
  reasons were written down.
- **A decision gets a module and a test (P2).** Tests are 22% of the changed
  lines, the only regression net in a codebase with no DOM tests.
- **600 code lines per file.** `main.ts` is at 571 code lines (969 with
  comments), and the limit forced the `ship-flow.ts` and `close-project.ts`
  splits, which made those parts testable.
- **A refusal explained where it is decided (errors-rule-1).** Drift between
  a check and its message deleted a card while saying it survived.
- **Never restart the running app (workflow-rule-1).** It is right until R1
  lands. After R1 it can be relaxed.

**Reliability**

- **A failure nobody caught keeps the app running (R6).** Every shell lives
  inside the process, which R1 would change but does not make wrong.
- **An unreadable `worktrees.json` stops the launch (errors-decision-2).**
  Nothing is open yet to lose, and an empty list would orphan worktrees.
- **Market fetches time out at 15 s each and fail one at a time.** The app
  starts offline (`markets-fetch.ts:12, 25-31`).
- **A missing project folder is kept.** `existingProjects` and
  `replacesProject` (`src/main/app/projects.ts:18-27`) keep the dead page and
  upgrade it when the folder is back.
- **The remote client losing its host mid-session** was not checked. Listed
  under Not done.

### D1. The exact pins are a sentence in a README, not a check — change

**What.** app/README "Dependency holds" says `electron`, the Agent SDK,
`marked`, `highlight.js` and `yaml` stay on exact versions, because the chat
code reaches SDK calls missing from its types.

**Against.** Nothing enforces it. A bump pull request turned the pins back
into caret ranges, and dc08326 ("Pin electron, the Agent SDK and marked
exactly again") had to put them back.

**Example.** Today: a routine `npm update` card writes `^0.3.316`, CI passes,
and the next fresh install takes an SDK that dropped `askSideQuestion`. `/btw`
fails on screen. With the alternative, the test fails on the caret.

**Alternative.** A vitest that reads `package.json` and fails when a held
dependency is not an exact version.

**Cost.** Small.

### D2. Windows installer and Linux packaging dependencies with no build that uses them — change (decision)

**What.** `electron-squirrel-startup` ships inside the app. The four Forge
makers and `@types/electron-squirrel-startup` came with the scaffold
(5685d95). CI runs on `ubuntu-latest` only and never runs `make`
(`.github/workflows/ci.yml`). The installed copy goes into
`~/.local/opt/dashboard` on Linux or `/Applications` on a mac, not through an
installer.

**Against.** They are code paths nobody runs. `maker-squirrel` pulls in
`electron-winstaller`, which is among the audit's moderate findings. The app
still has `win32` branches (`nvim-remote.ts`, `session-socket.ts`), so
Windows is half kept up.

**Alternative.** Decide whether Windows is a target. If it is not, drop
`electron-squirrel-startup`, its types, `maker-squirrel`, and any maker that
`make` is never run for, along with the `win32` branches. If it is, add a
Windows job to CI so the branches get run.

**Cost.** Small either way.

## Not done

- Secrets in the environment and the remote client on a dead network were not
  followed through. Every pane gets the app's whole `process.env` plus the
  `DASHBOARD_*` variables (`src/main/main.ts:217-225`), so any key in the
  launching environment is readable from every pane and, with S1, from a joined
  screen.

- No usage data says which features nobody uses. The log
  (`dashboard.log`) records kinds of events, not keys pressed, so "what the
  app does that nobody uses" is left open. The command runner across
  projects and the market cards are the first ones to check.
- The UX claims come from the installed 2.41.1 build in a demo instance with
  an empty project. Nothing was checked with real workers running.
